Checking edwm's memory use on FreeBSD
=====================================
All ps forms below are BSD-native and work as-is on FreeBSD. RSS and VSZ are
in kilobytes.


One-shot
--------
    ps -o pid,rss,vsz,%mem,comm -p $(pgrep -x dwm)


The measurement that actually matters: does it grow?
---------------------------------------------------
A window manager runs for weeks, so the trend matters far more than the
figure. Leave this running through a few hours of normal use:

    PID=$(pgrep -x dwm)
    while :; do
        printf '%s  %s kB\n' "$(date +%T)" "$(ps -o rss= -p $PID | tr -d ' ')"
        sleep 30
    done

To force the paths that actually allocate -- theme reloads, colour
allocation, icon decoding:

    PID=$(pgrep -x dwm)
    before=$(ps -o rss= -p $PID | tr -d ' ')
    for i in $(seq 1 50); do
        edwmctl theme nord;    sleep 0.2
        edwmctl theme gruvbox; sleep 0.2
    done
    after=$(ps -o rss= -p $PID | tr -d ' ')
    echo "before=$before  after=$after  delta=$((after - before)) kB"

Then open and close a tray applet's right-click menu about twenty times and
measure again. That exercises the menu tree, PNG decoding and X window churn
together, which is the heaviest thing edwm does.


FreeBSD-specific detail
-----------------------
    procstat -v $(pgrep -x dwm)     # every mapping; see the RES and PRES columns
    procstat -r $(pgrep -x dwm)     # resource usage and page faults

PRES (private resident) is the memory genuinely attributable to edwm rather
than shared with every other X client, so it is the more honest number. Read
the column header before trusting a script against it -- the units are pages,
so multiply by `pagesize`. These two commands are the only ones here that
were not verified before being written down, procstat being FreeBSD-only.


Is lower better?
================
Mostly, but RSS is the wrong headline number. Three things to keep in mind.

Ignore VSZ entirely. It is reserved address space, not memory in use. It
will look alarming -- hundreds of megabytes -- and means nothing.

Much of RSS is shared. Pages from libX11, libXft, libpng and libdbus are
counted in edwm's RSS and in every other X client's at the same time.
Trimming them would not return memory to the system, because something else
on the display is using them regardless.

edwm's RSS understates its real cost. The bar pixmap (screen width by bar
height), the tray windows and every allocated colour live in the X server's
address space, not edwm's. So measure both:

    ps -axo rss,comm | awk '$2 ~ /^(dwm|Xorg)$/ {s+=$1; \
        printf "  %-8s %8d kB\n", $2, $1} END {printf "  %-8s %8d kB\n", "TOTAL", s}'

What to care about is stability, not the absolute figure. Flat at 12 MB is
far better than starting at 6 MB and creeping to 60 MB over a week.


Reference numbers
-----------------
Measured on Linux during development, with D-Bus, the tray and applet menus
all active:

    idle                                    ~9.5 MB RSS
    across 200 theme reloads                8044 kB, unchanged
    across 75 tray icon changes             9556 kB, unchanged
    across 100 menu open/close cycles       9728 -> 9740 kB (allocator noise)

Stock dwm is roughly 3-4 MB, so the additions cost a few megabytes. That
flatness is the property worth reproducing; the absolute figure will differ
on FreeBSD, whose allocator and libraries are not the same, and edwm was
never run there during development.


Not a leak
----------
RSS climbing for the first minute or two after startx is normal. Fonts, icon
caches and library pages fault in lazily. Take the baseline once it plateaus,
not immediately.
